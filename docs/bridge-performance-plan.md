# Codex Feishu Bridge 极致响应改造规划

状态：执行中
目标版本：Desktop `0.8.2`
最后更新：2026-07-27

## 目标

在不降低现有会话、动态卡片、附件、MCP、Skills、Provider、工作区、恢复和控制面板能力的前提下，尽量缩短飞书消息到 Codex `turn/start` 之间的 Bridge 自身耗时，使热会话体验接近 Windows 本机 Codex CLI。

## 已确认的当前瓶颈

1. 普通消息会等待 CardKit 创建并发送完成后才启动 Codex。
2. 每次 app-server 任务结束都会关闭进程，下一条消息重复冷启动和 `initialize`。
3. 现有持久化事件去重能阻止已经处理过的重复事件，但不能阻止停机期间积压、重启后首次送达的旧消息。
4. 多会话直接共享一个 stdio app-server 客户端会带来通知串流风险，因此热复用必须使用独占租约，不能裸共享。

## 阶段一：本次交付

### 1. app-server 独占热租约池

- 每个 Bridge/Bot 默认最多保留 `maxConcurrent` 个 app-server。
- 每个 Server 同一时刻只服务一个任务；不同任务不会共用通知流。
- `initialize` 结果随热进程缓存，后续租约跳过重复初始化。
- 空闲默认保留 15 分钟后回收，可通过环境变量调整或关闭。
- 异常、超时、恢复重试时丢弃有问题的实例并冷启动回退。
- Bridge 关闭时终止全部热实例。

### 2. 飞书卡片与 Codex 并行启动

- 普通消息不再等待卡片打开后才调用 Codex。
- 卡片创建和 Codex 启动并行进行。
- 卡片尚未打开时，最新运行状态保留在内存；卡片就绪后立即刷新。
- 卡片失败仍使用原有 Markdown 兜底，不影响 Codex 任务。

### 3. 重启旧消息水位线

- 根据飞书事件时间识别启动前的陈旧消息。
- 默认保留短暂重启宽限窗口，避免正常重启边界上的新消息被误丢。
- 被拦截事件仍写入持久化去重，避免下一次重启再次出现。
- 无可靠时间戳的事件沿用现有处理逻辑。

### 4. 性能观测与回退

- 记录热/冷租约、进程等待、初始化、thread、turn/start 和卡片打开耗时。
- 保留 app-server 到 `codex exec` 的原有失败回退。
- 通过环境变量保留关闭热复用和调整 TTL 的能力。

## 阶段二：后续架构升级

阶段二不与本次低风险优化强行捆绑。只有阶段一的生产数据证明多 Bot 重复常驻仍是主要资源瓶颈时再实施：

- 每个 `CODEX_HOME` 一个本地 Runtime Broker。
- Broker 是 app-server 的唯一客户端，Bot 通过本地 IPC 请求任务。
- 同一 `threadId` 强制串行；不同 thread 按需并行。
- 默认一个热 Server，并发时有限扩展到两至三个。
- 加入工作区写锁、通知精确路由、崩溃隔离和版本回退。

## 验收标准

1. 根项目与 Desktop 全部自动化测试通过。
2. 打包后的 Engine 与协议代理 smoke test 通过。
3. 热会话日志明确显示复用 app-server 且 `initializeMs` 接近零。
4. 普通消息日志显示卡片创建不再阻塞 Codex 启动。
5. 陈旧事件被记录为跳过，不产生用户回复。
6. 当前 Windows 客户端升级后版本、Engine 提交和 Bot 恢复正常。
7. 旧 Windows 设备源码快进、测试通过、空闲 Bot 重启并健康。
8. 源码提交、`origin/main`、GitHub Release、新旧设备和已安装客户端版本一致。

## 风险控制

- 不让两个活动任务共享同一个 stdio app-server 客户端。
- 不重启存在 `active-runs.json` 活动条目的 Bot。
- 不覆盖旧设备未提交的本地改动。
- 发布前保留冷启动与 Markdown 兜底路径。
- 发现功能回归时优先关闭热复用，而不是牺牲现有功能。
