# 飞书卡片更新健壮性规划

## 背景

Codex Feishu Bridge 会把 Codex Agent Runtime 的运行状态渲染成飞书 CardKit 动态卡片。长任务里如果出现大量工具步骤，运行中卡片会反复更新，从第 1 步、第 2 步一直到数百步。

旧实现的问题不在 Codex 上下文本身，而在 Bridge 的卡片展示和传输方式：

- 运行中卡片会把所有历史步骤都渲染进同一张卡片。
- 每次更新飞书动态卡片时，实际发送的是整张卡片 JSON，不是只追加最新一行。
- Bridge 把完整 JSON 直接放进 `lark-cli --data <json>` 命令行参数。
- Windows 子进程命令行有长度限制，长任务会触发 `spawn ENAMETOOLONG`，导致卡片停在旧状态。

## 目标

保持现有功能不削减，同时让长任务更稳定：

- 飞书卡片继续实时展示任务进度。
- 用户仍能看到总步骤数和当前正在执行的步骤。
- 运行中卡片不再无限增长。
- CardKit 载荷不再受 Windows 命令行长度限制影响。
- 最终结果、错误步骤和本机日志仍保留完整排查路径。

## 方案

### 1. 运行中卡片限制历史步骤明细

运行中卡片默认只展示最近 20 个历史步骤，并把当前步骤单独展开。

示例：

修改前，一个任务跑到第 800 步时，卡片里会包含前面 799 个历史步骤摘要，再加当前步骤。

修改后，同样跑到第 800 步时，卡片显示：

- `800 个步骤已记录`
- `只显示最近 20 个历史步骤；更早 779 个已折叠，完整过程仍在本机日志中。`
- 当前步骤在下方展开

用户体验差别是：飞书里仍能知道任务没有停、已经跑到第几步、当前在干什么，但不会因为历史步骤太多导致卡片更新失败。

可配置项：

- `CODEX_FEISHU_CARD_MAX_RUNNING_TOOL_DETAILS`
- 默认值：`20`

### 2. CardKit JSON 改为安全传输

CardKit 创建和更新仍由 `lark-cli api` 完成，但大 JSON 不再直接塞进命令行。

Bridge 会先判断 JSON 的 UTF-8 字节长度：

- 小于等于阈值：继续使用 `--data <json>`。
- 超过阈值：写入临时 UTF-8 JSON 文件，并使用 `--data @file`。
- 调用结束后立即删除临时文件。

这能绕开 Windows 命令行长度限制，同时保持 `lark-cli` 的原有调用方式。

可配置项：

- `CODEX_FEISHU_LARK_DATA_FILE_THRESHOLD`
- 默认值：`8000`
- 设置为 `0` 时，所有 CardKit JSON 都走临时文件。

### 3. 最终卡片保持摘要策略

最终卡片不做功能削减：

- 最终回答仍正常展示。
- 成功步骤折叠为摘要。
- 错误步骤保留展开明细。
- 必要时可通过本机日志查看完整工具过程。

## 为什么这样改

只限制卡片展示不能完全解决命令行长度问题，因为某些任务的文本输出仍可能让卡片 JSON 变大。

只改 `--data @file` 也不够，因为飞书 CardKit 自身和用户阅读体验仍不适合无限增长的动态卡片。

因此两者需要同时做：

- 展示限流解决卡片膨胀和阅读体验。
- 文件传输解决 Windows `spawn ENAMETOOLONG`。

## 不改变的行为

- 不改变 Codex Agent Runtime 的执行逻辑。
- 不改变队列、会话、目标任务、附件下载、飞书消息收发能力。
- 不改变 Bot 实例数量和实例配置。
- 不改变最终回答发送逻辑。

## 重启要求

需要重启 Bridge 进程。

原因是 Node.js 进程启动时会把 `codex-feishu-bridge.mjs` 载入到进程内存里。磁盘代码改完后，已经运行的 Bridge 进程不会自动重新加载新代码。只有重启对应 Bot 的 Bridge 进程，新逻辑才会生效。
