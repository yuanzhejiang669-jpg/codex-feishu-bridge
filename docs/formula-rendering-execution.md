## 2026-07-27 - 三个月故障假设对抗性审查

1. **误把代码或货币识别成公式。** 验证发现代码围栏已有保护，但行内代码仍可能被扫描。已增加任意长度反引号行内代码范围保护，并用 `$25`、`` `$x^2$` ``、代码围栏、转义内容和未闭合定界符回归测试。
2. **网络抖动使 15 秒上限失效。** 图片上传原先允许两次完整超时重试，理论上会让总等待翻倍。已改为公式后处理单次上传、共享绝对截止时间，并把页面加载、截图和上传都限制在剩余预算内；失败直接保留原 Markdown。
3. **超长公式段落生成极高图片或打包后依赖缺失。** 已把单段上限从 2800 收紧到 1400 字符，超限保留原文；新增超长段落测试。随后重新 stage 桌面 engine，并分别用系统 Node 和客户端打包的 Node 运行公式烟雾测试，均成功加载 KaTeX/Playwright、发现 Edge、生成两张合法 PNG 并清理临时文件。

审查后公式单元测试通过 7 项。正式模块真实飞书 E2E 生成 `text -> formula_image -> text` 三段卡片；正常复测总计约 3.7 秒，其中公式渲染和上传约 2.0 秒。首次 E2E 遇到一次飞书网络重试而耗时约 48 秒，第二次恢复正常；正式公式管线现已通过共享 15 秒截止时间避免这类等待无限放大。

## 2026-07-27 - 0.8.5 安装版依赖热修复

- 用户实测发现 0.8.4 安装版仍显示原始 LaTeX。安装版 Bot 日志精确记录 `Cannot find package 'katex'`，并显示 `planned: 20, rendered: 0, failed: 20`。
- 根因不是公式识别或卡片生成逻辑，而是 Electron 对 `generated/engine` 的通用资源复制忽略了其嵌套 `node_modules`。源码和 staged-engine 测试会沿父目录找到仓库依赖，因此此前的验证产生了假阳性。
- 0.8.5 将 engine 的生产依赖树作为独立 `extraResources` 复制，并在 Windows/macOS 发布验证中强制检查 KaTeX、字体、Playwright 和依赖自检脚本。
- 新增真正隔离的安装结构回归：把打包后的完整 engine 复制到系统临时目录，使其无法沿目录向上借用源码仓库依赖，再用客户端内置 Node 加载 KaTeX/Playwright。
- Windows 发布验证额外用隔离后的 engine、客户端内置 Node 和系统 Edge 实际排版两段内容，必须得到 `rendered: 2, failed: 0`；浏览器不可用或跳过也视为发布失败。

### 热修复对抗性审查

1. **三个月后再次漏打生产依赖。** 已通过独立资源规则、安装目录文件断言和仓库外隔离加载三层验证；删除任一依赖或字体都会让 Release 构建失败。
2. **依赖虽然存在，但浏览器发现、启动或截图链路失效。** Windows Release 现在必须用系统 Edge 完成真实 PNG 渲染，不再只验证控制面板健康状态。
3. **staged engine 与源码或发布版本漂移。** 保留源码一致性测试，并在每次 `precheck`/构建前重新 stage；最终发布还会核对包版本、安装器版本、更新元数据和引擎提交。

本次审查只修复打包与验证链，没有改变公式数量阈值、卡片布局、流式输出或失败回退策略。

## 2026-07-28 - 密集公式完整性与延迟修复
