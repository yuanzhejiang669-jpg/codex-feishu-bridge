# Model reasoning capability registry

The Bridge and Windows desktop client share one offline, versioned registry:

```text
config\model-reasoning-capabilities.json
```

It records model-name patterns, accepted user effort values, the effective Codex value, the upstream meaning, an official source, and the last verification date. It is deliberately not inferred from `/models`: model-list endpoints normally expose IDs, not reliable reasoning semantics.

## Runtime contract

- The user's requested value remains visible and is persisted only after an explicit save or during new configuration creation.
- The mapped effective value is passed to Codex.
- Known impossible combinations are rejected before a request or configuration write.
- Unknown models use generic identity mapping and are visibly marked unverified; they are not silently treated as a known family.
- A known rule becomes visibly due for review after `reviewAfterDays` without blocking an otherwise working Bot.

## Updating the registry

1. Verify the current model documentation from the provider's official site.
2. Update the matching entry, mappings, `sourceUrl`, and `verifiedAt`.
3. Bump `registryVersion` even if only one model family changed.
4. Keep every canonical effort explicit in every mapping. Use `null` only when the model rejects that request.
5. Add aliases only when an official source or a real provider response confirms they are the same capability family.
6. Run the root and desktop checks.
7. Stage the desktop engine and confirm the staged registry passes the same checker.

```text
npm run check
cd apps\desktop
npm run check
npm run stage:engine
node generated\engine\scripts\check-model-reasoning-capabilities.mjs
npm run smoke:packaged-engine
```

Do not edit the copy under `apps\desktop\generated\engine`; it is generated by `stage-engine.cjs` and will be replaced.
